# 文档维护规范

中文 · [English](documentation.en.md)

[← 返回开发与协作](README.md)

本页补充贡献指南，说明如何让用户文档与快速变化的产品保持一致。

## 信息架构

- 首次完成任务的路径放 `getting-started/`；
- Web 操作与场景教程放 `guides/`；
- API、Channel 和客户端放 `channels/`；
- 配置、部署、升级、备份和排障放 `operations/`；
- 运行模型和信任边界放 `architecture/`；
- 构建、测试和发布维护放 `development/`。

不要为单页新建一级目录。根 README 只保留产品定位和最短成功路径，细节链接到权威页面。

## 双语

`docs/<path>.md` 为中文，`docs/<path>.en.md` 为英文。修改时同时打开和更新两个文件：

- 命令、路径、配置键、API 字段和产品术语保持一致；
- 不把第三方原文或协议值翻译成另一语义；
- 链接指向同语言 companion；
- 新页面必须从所属目录索引和根文档索引可发现。

## 截图与图表

任务关键界面使用 1–2 张截图；参考表和协议优先用文本、Mermaid 或结构化示例。

- 只使用从零构造的隔离伪造数据，不要把真实数据脱敏后当作演示数据；
- 截图前清空 Token、API Key、真实用户、会话、路径和运行记录；
- 中英文界面分别截图，不在两种文档中复用错误语言；
- 文件放 `docs/assets/screenshots/`，使用稳定、描述性名称；
- UI 行为变化时把截图更新纳入同一个 PR。

Mermaid 适合端到端流程、责任边界和时序；不要用它替代可以直接阅读的三行说明。

### 什么时候截图

截图应该帮助读者确认“我到了正确的位置”或“操作成功了”。优先截取：

- 首次设置、连接和授权等容易迷路的关键入口；
- 一个任务中最重要的操作状态或成功结果；
- Desktop 与 Web 中仅靠文字不容易辨认的布局。

不要为每个按钮截图，也不要用截图承载必须搜索、复制或长期维护的参数。界面变化频繁、步骤
可以用一两句话说清，或截图会暴露过多无关区域时，使用文字说明更合适。

### 准备隔离的伪造场景

截图不能来自个人或生产实例。使用一次性工作区、浏览器用户目录和运行数据目录，从空白状态
构造最小场景；不要加载个人 `.env`、`providers.json`、`data/`、浏览器同步账号或真实
Desktop 历史。截图结束后可以直接丢弃整个一次性环境。

伪造内容应当连贯、可读，并明显无效。例如：

| 内容 | 推荐示例 |
|---|---|
| 人物与搭档 | `Alice`、`Atlas` |
| 项目 | `demo-project` |
| 本地路径 | `/workspace/demo-project` |
| Provider / 模型 | `demo-provider` / `demo-model` |
| Token / API Key | 留空；必须展示格式时使用 `demo-token-not-valid` |
| Base URL | `https://example.invalid/v1` |
| 对话 | 与当前教程目标相关的两三条简短虚构消息 |
| 用量、任务和日志 | 少量固定的虚构记录，不复制真实记录 |

`.invalid` 是保留的无效域名，适合界面演示。不要使用看似真实的密钥前缀、公司内网域名、
个人用户名、主目录路径、仓库远端、IP、设备名或头像。伪造数据也不要包含不适合公开仓库的
内容。

如果界面必须连接一个 Provider 才能到达目标状态，使用专门的演示账号或本地 mock，并确保
它无法访问真实数据。不要为了截图临时关闭生产鉴权，也不要向一个真实 Provider 提交伪造
密钥反复试错。

### 采集步骤

1. 先写清截图要证明的用户结果，只保留与这个结果有关的界面区域。
2. 在一次性环境中填入上表一类的伪造数据，并关闭通知、自动填充、浏览器扩展浮层和其他
   无关窗口。
3. 固定窗口、缩放和主题；同一对中英文截图必须使用相同视口、界面状态和数据语义。当前
   Web 文档截图通常使用 `1600 × 1000`，相邻截图应保持一致。
4. 先切换到中文界面并采集 `-zh` 文件，再切换到英文界面，在相同状态采集 `-en` 文件。
   不要通过图像编辑把中文文字替换成英文。
5. 裁掉浏览器标签栏、地址栏、桌面、Dock、菜单栏和无关空白，但保留判断页面位置所需的
   导航与标题。
6. 放大检查每一个可见字段，然后再把文件加入文档。

界面截图优先保存为真正的 PNG；照片类素材才使用 JPEG。不要只修改扩展名。中英文 companion
使用同一基础名，例如：

```text
docs/assets/screenshots/admin-first-run-zh.png
docs/assets/screenshots/admin-first-run-en.png
```

文件名描述稳定的“界面 + 状态”，不要包含版本号、日期、人员姓名或自动生成 ID。若要加箭头
或编号，只添加不会被误认为产品控件的少量标注，并保留未标注的原始截图方便以后更新。

### 写入文档与复核

图片放在首次需要它的步骤之后，替代文本说明“哪个界面、什么状态”，不要写成“截图”。
图片下面注明它使用隔离的伪造数据：

```markdown
![Coworker 首次初始化向导](../assets/screenshots/admin-first-run-zh.png)

<p align="center"><sub>首次初始化向导 · 截图使用隔离的伪造配置，不包含真实密钥。</sub></p>
```

英文 companion 使用对应的 `-en` 文件、英文替代文本和英文说明。提交前由截图制作者以外的
视角再检查一次；如果不能确认某个值是否敏感，就重新构造场景并截图，不要只依赖模糊或遮挡。

## 写作与安全

- 以读者要完成的结果开头，再写前提和步骤；
- 明确成功反馈、失败恢复和破坏性操作影响；
- 命令必须从仓库当前脚本和 manifest 验证；
- 不建议删除数据、卷或强制覆盖作为普通排障第一步；
- 凭据、日志和导出包的示例只用占位符；
- 区分事实、版本限定行为和未来提案。

## 提交前检查

```bash
git diff --check
rg -n 'TODO|TBD|<token>|真实密钥' docs
file docs/assets/screenshots/*
```

另外人工检查：

- 所有相对链接和图片存在；
- 中英文标题、步骤、命令和警告成对；
- 新页面已进入索引；
- README 锚点在 GitHub 渲染下可达；
- 没有意外修改生成的 `src/coworker/web/`；
- 截图编码与扩展名一致，中英文图片的视口和状态匹配；
- 截图没有敏感信息，伪造数据也不会被误认为真实账号或密钥。

文档改动通常不需要运行全套代码测试；如果文档声明了 API、CLI、配置或平台行为，应运行
最小相关检查或直接从实现与测试核对，并在 PR 中说明未运行项。
